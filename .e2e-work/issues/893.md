# #893 — [SmsService][Report Concurrency] Shared gateway conflict is misclassified as a duplicate report

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/893

---

## Component

`[SmsService][Report Concurrency]` — terminal SMS report transaction and shared gateway daily counter.

## Evidence

- `ReportSmsResultCommandHandler.cs:52-71` updates the same `SmsGatewayDevice.SentToday` row for each successful SMS report.
- `:120-133` converts every `DbUpdateConcurrencyException` into HTTP 200 with `Concurrent report; treated as duplicate.`
- `SmsGatewayController.cs:116-124` documents that the Flutter gateway will not retry that response.
- The conflict can be between two different `SmsId` values that happen to update the same gateway `xmin`; the losing transaction rolls back its SMS/outbox changes but is acknowledged as if duplicate.
- `ReportSmsResultCommandHandlerTests.cs:193-205` encodes the blanket 200 response without re-querying durable SMS state.

## Steps to reproduce

1. Put SMS A and SMS B in `Sending` for the same gateway device.
2. Submit successful `Sent` reports for A and B concurrently against PostgreSQL.
3. Force both transactions to read the same gateway concurrency version.
4. Inspect both HTTP responses, both SMS rows, gateway `SentToday`, and outbox records.

## Actual result

One transaction commits; the other may conflict on the shared gateway row, roll back its SMS/outbox changes, yet return 200 as a duplicate. The gateway does not retry. The stale reaper can later return the still-`Sending` SMS to `Pending`, causing a physical duplicate send.

## Expected result

A conflict is treated as duplicate only after re-query proves that exact `SmsId` is already terminal. Different reports must retry/reload or update the counter atomically so both terminal states persist exactly once.

## Impact

Delivered messages can remain non-terminal, outbox events can disappear, quota can be wrong, and recipients can receive duplicate SMS messages.

## Acceptance criteria

- Re-query the reported `SmsId` after a concurrency conflict before classifying it as duplicate.
- Retry the transaction with a refreshed gateway row or use an atomic counter update.
- Add a real PostgreSQL integration test with two different concurrent `SmsId` reports.
- Assert both SMS rows are terminal, `SentToday` increases by two, and each outbox effect occurs exactly once.

## Verification performed

Current SMS claim/report suite passes (27/27); the existing concurrency unit test masks the rollback by accepting all conflicts as duplicates.
