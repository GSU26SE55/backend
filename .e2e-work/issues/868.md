# #868 — [IoT][Provisioning][Reliability] Partial NVS writes are acknowledged as a successful provision

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/868

---

## Component
IoT firmware — provisioning / persistent configuration

## Source evidence
- `firmware-esp32/src/provision/provision.cpp:138-144` writes polling interval, heartbeat interval, site ID, NTP server, firmware version, and the provisioned flag independently, while ignoring every `nvsPut*` result.
- `firmware-esp32/src/provision/provision.cpp:146-156` then unconditionally sets `outConfig.provisioned = true`, logs success, and returns `true`.
- The NVS wrapper returns `false` on open/write failure (`firmware-esp32/src/config/nvs_store.cpp:66-100`).
- On boot, `loadProvisioned()` trusts `provd == 1` and individually falls back missing fields (`provision.cpp:39-66`).

## Reproduction
1. Return a valid provisioning response.
2. Fault-inject a write failure for `siteid`, `pollIntS`, or `ntpsv`, while allowing the final `provd` write to succeed.
3. Observe `runProvisionFlow()` return true and runtime mark the device provisioned.
4. Reboot: `loadProvisioned()` sees `provd=1`, does not re-provision, but uses an empty site/default interval/default NTP for fields that failed.

The inverse partial write is also inconsistent: if data writes succeed but `provd` fails, the current runtime still reports success until reboot and provisioning repeats.

## Actual
A non-atomic partial configuration is reported as successfully provisioned. A device can become permanently marked provisioned without a valid site binding or operational settings.

## Expected
Provisioning configuration must be committed as one validated revision. The provisioned marker should be written last only after all fields succeed and read-back validation passes; partial state must remain unprovisioned and retry safely.

## Impact
Telemetry/environmental reporters can run with the wrong interval/site or remain disabled, while backend and firmware disagree about device state.

## Acceptance criteria
- Fail the flow if any required NVS write/read-back fails.
- Stage a versioned/checksummed configuration and commit the provisioned flag atomically or with crash-safe recovery.
- Validate required `siteId` and other response fields before persistence.
- Add fault-injection and power-loss tests at every write boundary and reboot after each partial state.
