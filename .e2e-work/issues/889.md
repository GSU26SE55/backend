# #889 — [AuthService][Sessions] Refreshing at the session cap revokes an unrelated active device

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/889

---

## Component
AuthService — refresh-token rotation and session-cap enforcement

## Evidence
- `RefreshTokenCommandHandler.cs:157-176` adds the replacement and marks the current token Used only in the change tracker.
- Lines 183-189 publish `SessionCreatedNotification` before SaveChanges.
- `SessionCreatedNotificationHandler.cs:48-62` queries DB tokens that still include the rotating token as Active, then always adds one projected session.
- Rotation is therefore counted as a new device before the old DB row is committed Used.

## Reproduction
With max sessions=3 and active A/B/C, refresh C. C is Used only in memory and D is added. The notification DB query still sees A/B/C, calculates 3+1=4, and revokes unrelated oldest A. After commit only B/D remain although rotation should preserve three active devices.

## Actual
Refreshing at cap logs out an unrelated device and reduces the real active count.

## Expected
Rotation replaces one session 1:1 and must not trigger new-device eviction.

## Acceptance criteria
- Distinguish new issuance from rotation or pass the replaced session identity.
- Compute projected active count transactionally with consistent locking/concurrency behavior.
- PostgreSQL integration tests at cap refresh newest/oldest/middle.
- Exactly N active sessions remain and only the rotated token becomes Used.
- Concurrent refresh/login tests prevent over-cap and unrelated revocation.
