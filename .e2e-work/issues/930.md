# #930 — [NotificationService][Preferences] Invalid timezone is persisted or causes 500 instead of controlled validation

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/930

---

## Component

`NotificationService` notification preference validation and quiet-hours dispatch.

## Summary

The application accepts timezone strings up to 100 characters while the database column is limited to 64, and it never verifies that the timezone exists. A 65–100 character value can pass validation then fail persistence/500; an invalid short ID is persisted and silently treated as `Asia/Ho_Chi_Minh`, so quiet hours run in a timezone the user never selected.

## Evidence

- `UpdateNotificationPreferenceCommand.cs:44-47` allows timezone length up to 100.
- `NotificationPreferenceConfiguration.cs:23-25` limits the column to 64.
- The command validator does not call timezone lookup or validate an IANA/Windows ID.
- `NotificationDispatcher.cs:632-636` catches lookup errors and silently falls back to `Asia/Ho_Chi_Minh`.
- The command has no direct boundary/semantic test.

## Reproduction

1. PUT `/api/notification-preferences` with a timezone of 65–100 characters: validation passes, then persistence can throw/truncate and return 500.
2. PUT with `"Mars/Olympus"`: API persists it successfully.
3. During quiet-hour evaluation, lookup fails and dispatcher uses Vietnam time without notifying the user.

## Impact

- API-valid input can cause an internal server error.
- Notifications can be sent during the user's intended quiet hours or delayed incorrectly.
- Stored preferences do not reflect actual dispatch behavior.

## Acceptance criteria

- Align application and database maximum lengths.
- Validate supported timezone IDs using `TimeZoneInfo` or a canonical IANA list before persistence.
- Do not silently substitute a different timezone for client-supplied invalid input.
- Validate quiet-hours start/end as a coherent pair.
- Add 64/65 boundary, valid/invalid timezone, DST, and round-trip dispatch tests.
