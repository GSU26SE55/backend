# #939 — [AuthService][Reactivation][Lifecycle] Reused email makes 90-day account restore crash with a unique-index 500

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/939

---

## Component

`[AuthService][Account Reactivation][Lifecycle][PostgreSQL]`

## Severity

P2 High — a documented, valid soft-delete/email-reuse lifecycle ends in an uncontrolled unique-index 500.

## Source evidence

- `services/AuthService/src/AuthService.Infrastructure/Persistence/Configurations/AccountConfiguration.cs:157-161` makes email unique only for active rows (`WHERE is_deleted = false`), intentionally releasing an email after soft deletion.
- `ReactivateVerifyCommandHandler.cs:33-69` loads the old deleted account, clears `IsDeleted`, and calls `SaveChangesAsync` without checking whether another active account now owns that email.
- The handler does not catch/map `DbUpdateException` or PostgreSQL `23505` to a domain conflict.
- `docs/api-auth.md:4588` explicitly describes this exact lifecycle and says reactivate-verify should perform a `taken` check and return a controlled UX conflict; that check is absent.

## Deterministic reproduction

1. Account A registers with `user@example.com`.
2. A is soft-deleted within the 90-day reactivation window.
3. Account B registers using the now-released `user@example.com`; this is allowed by the partial unique index.
4. Request reactivation for A and submit its valid OTP to reactivate-verify.
5. The handler changes A to `is_deleted=false` and saves.
6. PostgreSQL rejects the update because B is already active with that email; the endpoint returns an uncontrolled HTTP 500 and A remains deleted.

## Actual

The application allows the documented preconditions, then relies on the database to throw an unhandled uniqueness exception during restore.

## Expected

Reactivation must detect that the identity has been reclaimed and return a stable conflict response without attempting a violating update.

## Impact

- A valid 90-day reactivation flow crashes at its final step.
- Users receive a server error instead of the documented actionable conflict.
- Database exception details may leak through logs/diagnostics, and retrying the same OTP cannot succeed.

## Acceptance criteria

- Check for another active account owning the normalized email before restore.
- Return HTTP 409 with a stable error code/message when the email is taken.
- Retain the DB unique index as the final concurrency guard.
- Catch a concurrent `23505` race and map it to the same conflict response.
- Define whether the OTP remains usable or is invalidated after the conflict.
- Add handler and HTTP integration tests for normal restore, reused email, concurrent claim/restore, expired window, and OTP replay.

## Dedupe

No existing issue through #938 covers account-reactivation email reuse. This is separate from registration, merge, password reset, and session-cap defects.
