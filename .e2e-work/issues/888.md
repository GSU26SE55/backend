# #888 — [FileStorageService][Consistency] Object deletion before metadata commit leaves live metadata pointing to missing content

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/888

---

## Component
FileStorageService — delete transaction consistency

## Evidence
- `DeleteFileCommandHandler.cs:43-47` deletes the object first, then soft-deletes metadata and calls SaveChanges.
- `DeleteFileByIdCommandHandler.cs:42-46` has the same ordering.
- `FilesController.cs:448` documents that storage deletion can succeed while metadata save fails and require manual cleanup.
- Existing tests cover only the happy path.

## Reproduction
1. Create Ready metadata pointing to an existing object.
2. Let object-storage DeleteAsync succeed.
3. Inject DbUpdateException from SaveChangesAsync.
4. Request returns 500; metadata remains live/Ready while content is gone, and later metadata/presigned/download flows fail at storage.

## Actual
A partial failure creates a durable metadata-to-object split with no automatic recovery.

## Expected
Deletion must be a recoverable state machine/outbox workflow or provide compensation/reconciliation; retries must be idempotent.

## Acceptance criteria
- Introduce deletion state/outbox/background cleanup or safe compensation.
- Handle object-already-missing plus live metadata idempotently.
- Fault tests for storage success+DB failure, DB success+storage failure, and repeated/concurrent delete.
- Add metadata/object reconciliation metric and repair job.
- No Ready metadata may permanently reference missing content after recovery.
