# #891 — [IoT][Firmware][Supply Chain] Caret dependency ranges make device artifacts non-reproducible

Priority: priority: P3
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/891

---

## Component
IoT firmware — PlatformIO dependency and toolchain reproducibility

## Evidence
- `firmware-esp32/platformio.ini:35-46` claims versions are pinned for reproducibility but every library uses a caret range such as `^2.8`, `^7.1.0`, or `^0.6.0`.
- The platform itself uses `espressif32 @ ^6.7.0` at line 52.
- The IoT repository tracks no PlatformIO lock file or `.pio` resolved dependency metadata.
- A current clean build already resolves broader versions, for example ArduinoJson 7.4.3 from `^7.1.0`, INA226 0.6.6 from `^0.6.0`, and platform 6.13.0 from `^6.7.0`.

## Reproduction
Run the same clean build on fresh machines or after registry updates. PlatformIO is allowed to select different platform/framework/library versions while the source commit is unchanged, producing a different firmware binary and potentially different hardware/protocol behavior.

## Actual
A commit does not uniquely determine its device artifact, despite source comments and production expectations.

## Expected
Production firmware dependencies/toolchain are locked to exact reviewed versions with controlled update workflow and verifiable artifact provenance.

## Impact
Unreviewed dependency changes can alter MQTT, JSON, I2C/Modbus, TLS, filesystem, or OTA behavior and make field incidents impossible to reproduce from the Git commit alone.

## Acceptance criteria
- Pin exact platform and direct dependency versions or commit a supported lock mechanism.
- Record framework/toolchain package versions and artifact hash/SBOM in CI.
- Build the same commit twice in clean environments and assert identical firmware hash.
- Dependency upgrades occur via explicit reviewed changes with mock+real build and hardware/regression gates.
