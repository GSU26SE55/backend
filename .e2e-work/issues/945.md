# #945 — [AuthService][Reactivation][Profiles] Reactivated accounts retain hidden profile tombstones that break later profile writes

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/945

---

## Component

`[AuthService][Account Reactivation][AccountProfile][StaffProfile]`

## Severity

P2 High — successful account reactivation leaves hidden one-to-one profile tombstones that make profile APIs fail with unique-index 500 errors.

## Source evidence

- `DeleteAccountCommandHandler.cs:70-97` anonymizes and soft-deletes `AccountProfile` and `StaffProfile`, while retaining the account identity for the 90-day reactivation path.
- `ReactivateVerifyCommandHandler.cs` restores only the `Account`; it does not restore, remove, or otherwise reconcile either profile row.
- `AccountProfileConfiguration.cs:66,75` and `StaffProfileConfiguration.cs:62,80` use unconditional unique `AccountId` indexes plus global filters hiding soft-deleted rows.
- `UpdateMyProfile` (`:30-79`), `UpdateStaffProfile` (`:47-60`), and `AddStaffSkill` (`:31-43`) query only active profiles and create a new row when none is visible.
- The hidden tombstone still owns the same unique `AccountId`, so the insert fails with PostgreSQL `23505`.

## Deterministic reproduction

1. Create an account with an AccountProfile; for Staff, also create StaffProfile.
2. Admin-delete the account, which soft-deletes/anonymizes the profile rows.
3. Reactivate the account within 90 days using a valid OTP and an email that has not been reclaimed. Reactivation returns 200.
4. Call `UpdateMyProfile`; for Staff, also try admin staff-profile update or add-skill.
5. Each handler sees no active profile and attempts a new row with the restored AccountId.
6. The unconditional one-to-one unique index rejects it; the operation returns 500.

## Actual

Account status is restored but its dependent aggregate remains in a hidden, uniqueness-blocking deleted state.

## Expected

Reactivation must atomically reconcile every restorable dependent row, or profile commands must intentionally restore/reuse the tombstone before inserting.

## Impact

- Reactivated customers cannot maintain their profile.
- Reactivated staff cannot restore operational profile/skill data and may be unusable for assignment workflows.
- The API reports successful account recovery even though core post-login features are broken.

## Acceptance criteria

- Define which anonymized profile fields can/should be restored and which must be re-entered.
- Reconcile AccountProfile and StaffProfile atomically during reactivation, or restore tombstones on first profile mutation.
- Never insert a duplicate one-to-one row while a deleted row owns the AccountId.
- Map unavoidable concurrency conflicts to a controlled response.
- Add end-to-end admin-delete→reactivate→customer-profile and staff-profile/skill tests.
- Verify audit, privacy/anonymization, and role-specific profile invariants after restore.

## Dedupe

Distinct from #939: #939 makes reactivation itself fail only when the email was reused; this issue occurs after a successful reactivation with no email collision.
