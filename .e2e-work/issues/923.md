# #923 — [IoT][BMS][Redundancy] Primary Modbus failure suppresses healthy INA226 and DS18B20 telemetry

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/923

---

## Component

`IoT firmware` — real BMS source dispatcher and redundant INA226/DS18B20 telemetry.

## Summary

The real firmware derives the serial list for INA226 and DS18B20 exclusively from successful Modbus BMS readings. If the RS485 bus or all BMS units fail, `nBms=0`, both independent sensor builders receive an empty list, and no telemetry is published even when INA226/DS18B20 are healthy. The implementation therefore removes the very redundancy that is intended to preserve observation when one source fails.

## Evidence

- `../iot/firmware-esp32/src/bms/bms_source.cpp:69-75` polls BMS first into `bmsReadings`.
- `bms_source.cpp:77-88` creates `serials[]` only from those successful BMS results and passes `nBms` to both INA226 and DS18B20 builders.
- `bms_source.cpp:90-112` also iterates merge output only while `b < nBms`.
- With `nBms=0`, `bmsSourcePollAll` returns 0; `../iot/firmware-esp32/src/main.cpp:248-255` exits `ingestOnce` without MQTT/HTTPS publication.
- `../iot/docs/glossary.md:74` states the redundancy requirement: BMS + INA226 must ensure one failed source is still detectable.
- `../iot/overall.iot.md:88-99,421-442` defines INA226/DS18B20 as independent cross-source sensors.
- `overall.md:7949,9685-9688` requires three readings per battery and explicitly defines BMS versus INA226 as independent sources.

## Deterministic reproduction

1. Run `esp32-s3-real` with healthy INA226 and DS18B20 devices and valid static battery mappings.
2. Disconnect the RS485 bus or make every Modbus slave time out.
3. `modbusReadMultiDrop` returns 0.
4. `ina226BuildRedundantReadings(serials, 0, ...)` and `ds18b20BuildExternalTempReadings(serials, 0, ...)` produce 0 without sampling/publishing mapped batteries.
5. Merge loop runs zero times, `bmsSourcePollAll` returns 0, and the ingest path publishes nothing.

## Actual result

Failure of the primary BMS source suppresses all independent redundant/external sensor data.

## Expected result

Every configured battery mapping must be sampled independently by each available sensor source. A BMS failure should omit only the primary reading and preserve INA226/DS18B20 readings with correct battery identity.

## Impact

- Primary BMS failure creates a complete telemetry blackout instead of degraded but observable operation.
- Cross-source monitoring cannot distinguish BMS failure from gateway outage.
- Independent voltage/current/temperature safety data is lost exactly when redundancy is needed.
- Downstream offline/anomaly/ticket behavior receives no evidence of the partial hardware failure.

## Acceptance criteria

- Build the battery serial/mapping list from provisioned/static battery mappings, not successful BMS results.
- Poll and merge BMS, INA226, and DS18B20 independently; preserve source tags and identity.
- Emit partial batches when one or two sources fail.
- Expose per-source health/failure telemetry.
- Add real-path tests for BMS-only failure, INA-only failure, DS-only failure, mixed per-battery failure, and all sources failed.
- Assert a healthy redundant source remains published when `nBms=0`.
