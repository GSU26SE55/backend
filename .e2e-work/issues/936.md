# #936 — [IoT][LittleFS][Data Loss] Automatic mount recovery erases the offline queue and MQTT CA certificate

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/936

---

## Component

`[IoT][LittleFS][Offline Queue][MQTT TLS]`

## Severity

P2 High — a mount failure silently erases durable telemetry and the provisioned MQTT trust anchor.

## Source evidence

- `firmware-esp32/src/queue/local_queue.cpp:105-108` mounts LittleFS with `LittleFS.begin(true)`, enabling automatic format on mount failure.
- `firmware-esp32/src/net/mqtt_client.cpp:71-74` independently uses the same `LittleFS.begin(true)` behavior while loading the MQTT CA certificate.
- The same filesystem stores `/queue/*.json`, `/queue/*.idem`, and `MQTT_CA_CERT_PATH`.
- `main.cpp` calls `queueBegin()` before `mqttBegin()` during every boot, so the queue path can format the shared partition before MQTT checks whether its CA still exists.

## Reproduction

1. Put one or more offline telemetry batches in `/queue/` and a valid CA at `MQTT_CA_CERT_PATH`.
2. Reboot while fault-injecting a recoverable/transient LittleFS mount failure or filesystem metadata corruption.
3. `queueBegin()` calls `LittleFS.begin(true)`; the library formats the partition and retries the mount.
4. Queue startup reports an empty queue rather than a durability fault.
5. `mqttBegin()` then cannot find the CA certificate and permanently falls back to HTTPS-only until the filesystem image/certificate is reprovisioned.

The same destructive behavior can be triggered from `loadCaCert()` if it is the first effective mount caller in another startup path.

## Actual

The firmware treats a mount problem as permission to format shared persistent storage without confirmation, backup, quarantine, recovery attempt, or a data-loss signal.

## Expected

Production startup must fail safe: preserve the partition, expose the storage fault, and attempt explicit/recoverable repair. Formatting must be a deliberate maintenance/factory-reset operation, never an automatic mount side effect.

## Impact

- All queued telemetry can be lost precisely after an outage or unstable-power event.
- The MQTT CA trust anchor is erased, disabling the primary transport after reboot.
- Operators see queue depth zero and an apparently unrelated missing-CA error, obscuring the destructive root cause.

## Acceptance criteria

- Mount production LittleFS with `formatOnFail=false`.
- Put queue data and immutable/provisioned trust anchors in separately managed partitions or provide an atomic restore path.
- Add explicit, authenticated factory-reset/reformat behavior with clear data-loss warnings.
- Emit durable diagnostics/metrics when mount, recovery, or integrity validation fails.
- Add reboot/fault-injection tests proving transient mount failure and corrupt queue entries do not erase unaffected batches or the CA.
- Verify MQTT and HTTPS fallback behavior after storage recovery.

## Dedupe

Distinct from #883 (enqueue/short-read atomicity), #835 (missing idempotency sidecar), and #892 (certificate-script credential exposure). This issue is destructive automatic formatting of the shared persistence partition during mount.
