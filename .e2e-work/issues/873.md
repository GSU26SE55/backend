# #873 — [AuthService][Google OAuth][Security] Access and refresh tokens are logged verbatim

Priority: priority: P1
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/873

---

## Component
AuthService — Google OAuth token exchange logging

## Evidence
- `GoogleOAuthHelper.cs:127-155` reads the raw Google token response and logs the complete body for non-2xx, invalid/empty payload, and successful payload missing `id_token`.
- `GoogleOAuthHelper.cs:194-200` models the body with `access_token` and `refresh_token`.
- Current tests use `NullLogger` and do not assert redaction.

## Deterministic reproduction
Stub the token endpoint with HTTP 200 containing an `access_token`, `refresh_token`, and `token_type`, but omit `id_token`. The helper returns null and executes the warning at lines 152-155 with the entire response body, exposing both seeded tokens in logs.

## Actual
OAuth credentials can be copied verbatim into application/centralized logs on common provider error or partial-response paths.

## Expected
Never log authorization codes, client secrets, access tokens, refresh tokens, ID tokens, or raw provider bodies. Log only allowlisted diagnostic fields, status, safe provider error code, and correlation ID.

## Impact
Anyone with log access can obtain live Google credentials and access user data until expiry/revocation.

## Acceptance criteria
- Remove raw-body logging or sanitize using an explicit allowlist.
- Ensure exception logging cannot serialize the secret payload.
- Add capturing-logger tests for non-2xx, invalid JSON, missing `id_token`, and successful exchange.
- Assert seeded secrets never occur in messages, scopes, structured properties, traces, or metrics.
