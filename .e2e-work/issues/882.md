# #882 — [IoT][DS18B20][Telemetry] One disconnected sensor drops external temperatures for every later battery

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/882

---

## Component
IoT firmware — real-BMS multi-source merge and DS18B20 failure path

## Evidence
- `firmware-esp32/src/sensor/ds18b20.cpp:86-100` skips a disconnected sensor but writes every later valid reading into the compacted `out[produced]` array.
- Each compacted reading retains the original later battery serial (`ds18b20.cpp:103-108`).
- `firmware-esp32/src/bms/bms_source.cpp:94-110` incorrectly assumes DS output index still equals battery index and checks only `dsReadings[b]` against `bmsReadings[b]`.

## Deterministic reproduction
For serials `[BAT0,BAT1,BAT2,BAT3]`, disconnect DS sensor 0. The DS builder returns compacted `[BAT1,BAT2,BAT3]` with `nDs=3`. Merge compares BAT1 to BAT0, BAT2 to BAT1, BAT3 to BAT2, then skips BAT3 because `b=3` is not `< nDs`. No external-temperature reading is emitted. If sensor 1 fails, BAT0 survives and every later battery is dropped.

## Actual
A single sensor failure shifts the compact array and suppresses all downstream DS18B20 readings, even though those sensors were read successfully.

## Expected
Merge by stable battery serial/address mapping, not array position. A failed sensor must affect only its mapped battery.

## Impact
Loss of temperature redundancy across multiple batteries hides thermal mismatch and degrades safety monitoring during a common single-probe disconnect.

## Acceptance criteria
- Join source readings by battery serial or explicit sensor-address mapping.
- Keep per-battery failure isolation with no positional compaction assumption.
- Add tests for first/middle/last and multiple disconnected probes, reordered sensor enumeration, and recovery.
- E2E confirms healthy later batteries continue to publish external-temperature rows.
