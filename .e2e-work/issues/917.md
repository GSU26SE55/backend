# #917 — [BatteryService][IoT][OTA Contract] Valid release notes truncate firmware-check JSON and block updates

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/917

---

## Component

`BatteryService` ↔ `IoT firmware` — OTA firmware-check response contract.

## Summary

BatteryService accepts and stores unbounded firmware `ReleaseNotes`, while ESP32 firmware copies the complete firmware-check response into a fixed 2,048-byte buffer. Any valid release whose JSON exceeds 2,047 bytes is silently truncated; JSON parsing then fails and the device never downloads or applies the update.

## Evidence

- `services/BatteryService/src/BatteryService.Application/CQRS/Command/IotFirmware/CreateIotFirmwareReleaseCommand.cs:23-24,36-51` accepts `ReleaseNotes` but imposes no size limit.
- `services/BatteryService/src/BatteryService.Infrastructure/Persistence/Configurations/IotFirmwareReleaseConfiguration.cs:40-41` maps `release_notes` with no maximum length.
- `services/BatteryService/src/BatteryService.Application/DTOs/IotDeviceDto.cs:123-160` returns both alias pairs (`UpdateAvailable`/`HasUpdate`, `ArtifactUrl`/`DownloadUrl`) plus the full `ReleaseNotes`, increasing the response size.
- `services/BatteryService/src/BatteryService.Application/CQRS/Handler/IotDevice/DeviceLifecycleHandlers.cs:205-255` creates a Pending update log and returns the full notes.
- `../iot/firmware-esp32/src/ota/ota_update.cpp:298-310` allocates exactly `char resp[2048]` and aborts when truncated JSON cannot be parsed.
- `../iot/firmware-esp32/src/net/http_client.cpp:36-51` copies only `fullBufLen - 1` bytes and returns the truncated length without exposing a truncation error.

## Deterministic reproduction

1. Create and publish a valid firmware release with a `ReleaseNotes` string of 2,500 ASCII characters; the backend validator and database accept it.
2. Assign it as the target of a device and call `GET /api/iot-devices/firmware-check?currentVersion=<old>`.
3. The JSON response necessarily exceeds the firmware's 2,047-byte payload capacity.
4. `copyResponseFull` truncates the body and null-terminates it; `deserializeJson` returns an error.
5. The device logs `firmware-check JSON parse FAIL (response truncated?)` and never reaches `downloadAndFlash`.
6. On a later poll, BatteryService creates another Pending update log because the target remains different.

## Actual result

A release accepted by BatteryService cannot be consumed by the shipped firmware. The update is silently skipped after HTTP 200, while Pending attempt logs can accumulate.

## Expected result

Every response permitted by the backend contract must fit the device protocol, or the firmware must stream/parse safely and explicitly reject over-limit payloads before creating an update attempt.

## Impact

- Required safety/security firmware can be blocked by ordinary release notes.
- Operators see Pending attempts but devices never report Downloading/Failed.
- Repeated polls create misleading orphan Pending logs.

## Acceptance criteria

- Define and enforce a shared maximum response/release-notes size, or omit release notes from the device check payload.
- Do not serialize duplicate alias fields on the wire.
- Firmware must detect `Content-Length`/buffer overflow and report a terminal, diagnosable failure rather than parse a truncated body.
- Do not create repeated Pending logs for responses the device cannot consume.
- Add a cross-repository contract test at the maximum permitted notes/URL lengths and an over-limit negative test.
