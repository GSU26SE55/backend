# #914 — [IoT][HTTPS Fallback][Backoff] Live batches bypass backoff and every device uses identical jitter

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/914

---

## Component

`[IoT][HTTPS Fallback][Backoff]` — firmware ingest admission during BatteryService/network failure and fleet retry jitter.

## Source evidence

- `firmware-esp32/src/main.cpp:304-313` calls `s_backoff.recordFailure()` after a transient POST and logs the delay.
- `tryFlushQueue()` at `main.cpp:318-365` respects `s_backoff.nextRetryAt()`, but the normal ingest scheduler at `main.cpp:524-543` never checks it before calling `ingestOnce()` and `postBatch()`.
- Therefore every newly sampled batch performs another HTTP request at `pollInterval` even while the logged backoff window is active; only old queue flushing is delayed.
- `net/backoff.cpp:25-31` initializes one process-global jitter RNG with constant `0x12345678`.
- `Backoff::setRandomSeed()` is used by tests only and is never called at firmware startup, despite `backoff.h` claiming a runtime/default seed. Every device follows the same jitter sequence.

## Deterministic reproduction

1. Configure fallback HTTPS with a 5-second poll and make BatteryService return 503 or 429 continuously.
2. Observe the first failures increase/log backoff (eventually tens of seconds to five minutes).
3. Capture requests during a period where `millis() < nextRetryAt()`.
4. Observe a new POST every five seconds from the normal ingest path; only `tryFlushQueue()` is suppressed.
5. Start two devices from the same firmware and compare their delay sequence; both generate the same jitter values because the seed is constant.

## Actual result

The firmware advertises exponential backoff but continues sending fixed-rate live requests through the entire backoff window. A fleet retries in a synchronized deterministic pattern, and repeated live failures keep moving the shared queue-flush deadline.

## Expected result

An active retry/admission window applies to all HTTP attempts for the failed dependency. New samples are durably queued without another request until the deadline. Devices use independent entropy and honor server retry guidance.

## Impact

A BatteryService outage or 429 overload is amplified by every gateway (for a 5-second poll, up to 12 requests/minute/device), delaying recovery and defeating the intended thundering-herd protection. Oldest queued data is also starved behind ongoing live failures.

## Acceptance criteria

- Gate live fallback POST and queue flush through one overflow-safe retry/admission controller.
- While backoff is active, enqueue new telemetry directly without attempting HTTP.
- Seed jitter from per-device/boot entropy (for example `esp_random` plus device identity), not a fleet-wide constant.
- Parse/honor bounded `Retry-After` for 429/503 where available.
- Ensure successful recovery drains oldest-first without new data starving queued records.
- Add native/simulator tests for active-window suppression, increasing/capped delay, two-device jitter divergence, 429/503, millis wrap, and recovery ordering.
- Add request/queue/backoff metrics that distinguish live attempts from flush attempts.

## Dedupe note

Distinct from #741 (environmental incident permanent-4xx tight retry) and #883/#835 (LittleFS queue atomicity). This issue is the main telemetry HTTPS admission/backoff path under transient failure.
