# #937 — [AuthService][Shared JWT][Key Rotation] Previous signing key is ignored by ASP.NET authentication across all services

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/937

---

## Component

`[AuthService][ApiGateway][Shared JWT][All Resource Services]`

## Severity

P2 High — planned zero-downtime signing-key rotation invalidates every existing access token across all ASP.NET authorization paths.

## Source evidence

- `services/AuthService/src/AuthService.Infrastructure/Implements/Helpers/JwtHelper.cs:61-75` emits a `kid` header for the configured signing key.
- `JwtHelper.cs:124-150` manually validates against both `JwtSettings:SecretKey` and `JwtSettings:PreviousSecretKey`, with current/previous key IDs.
- `deploy/helm/solar-battery/templates/shared/secret.yaml:48-53` explicitly documents a one-hour previous-key grace period during rotation.
- The real `[Authorize]` pipeline used by Auth, Gateway, Battery, Ticket, Notification, FileStorage, SMS, and Audit is `shared/src/SharedInfrastructure/DependencyInjection/Extensions/AddJWTAuthenticationAuthorization.cs:15-33`.
- That shared JwtBearer registration reads only `SecretKey` and configures a singular `IssuerSigningKey`; it never reads `PreviousSecretKey`, `SigningKeyId`, or `PreviousSigningKeyId`.

## Reproduction

1. Configure current key/key ID as v1 and issue a valid access token.
2. Rotate to current v2 while setting `PreviousSecretKey=v1` and `PreviousSigningKeyId=v1`, as documented by the chart.
3. Call `JwtHelper.ValidateToken(oldV1Token)`: it succeeds during the grace period.
4. Send the same token to any `[Authorize]` endpoint in AuthService or another backend service.
5. JwtBearer rejects it with HTTP 401 / `INVALID_SIGNATURE` because only v2 is in `IssuerSigningKey`.

## Actual

Manual token validation and actual HTTP authorization implement different key sets. The configured previous key is ineffective for real API requests.

## Expected

Every token-validation path must resolve `kid` against the same bounded current/previous key ring and honor the documented grace period.

## Impact

- Every active user is forced out during a routine signing-key rotation.
- All services fail simultaneously, creating a platform-wide authentication incident.
- Healthier current-key login/refresh does not protect in-flight clients or requests from mass 401 failures.

## Acceptance criteria

- Configure JwtBearer `IssuerSigningKeys` or a safe `IssuerSigningKeyResolver` with current and previous keys/IDs.
- Reject unknown/missing `kid` according to one explicit compatibility policy.
- Keep helper, Gateway, AuthService, and every direct resource-service port semantically identical.
- Remove the previous key after the bounded grace period without restart ambiguity.
- Add integration tests that issue v1, rotate to v2+previous-v1, and prove v1/v2 behavior across Auth, Gateway, Battery, Ticket, Notification, and FileStorage.
- Add negative tests for wrong key, wrong `kid`, expired token, and previous-key removal.

## Verification gap

Existing Shared JWT tests pass 6/6 and JwtHelper tests pass 19/19, but neither suite exercises previous-key JwtBearer authorization.

## Dedupe

Distinct from #925, which covers revocation enforcement. This issue concerns signature validation during an explicitly supported key-rotation grace window.
