# #931 — [BatteryService][IoT][Offline Detection] Valid heartbeat intervals exceed the global threshold and create false offline alerts

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/931

---

## Component

`BatteryService` — IoT device heartbeat configuration and offline detection.

## Summary

Admin APIs accept `HeartbeatIntervalSeconds` up to 3,600 seconds, but offline detection uses one global 300-second threshold and never considers each device's configured interval. A valid low-frequency device is marked Offline, generates an alert/event, and then flips back Active on its next scheduled heartbeat. The API documentation itself warns of the false positive but still permits the incompatible configuration.

## Evidence

- `services/BatteryService/src/BatteryService.Application/CQRS/Command/IotDevice/CreateIotDeviceCommand.cs:50-51` and `UpdateIotDeviceCommand.cs:46-47` accept intervals in `[10, 3600]`.
- `services/BatteryService/src/BatteryService.Application/Services/IotDeviceOfflineDetectionService.cs:30-42` computes a single `now - offlineAfterSeconds` cutoff for all devices and does not read `HeartbeatIntervalSeconds`.
- `IotDeviceOfflineDetectionService.cs:47-101` marks the device Offline and creates an alert/outbox event.
- `services/BatteryService/src/BatteryService.Infrastructure/BackgroundServices/IotDeviceOfflineDetectionBackgroundService.cs:33` defaults the global threshold to 300 seconds.
- `services/BatteryService/src/BatteryService.Api/Controllers/IotDevicesController.cs:133-138` explicitly documents that setting heartbeat near/above the threshold causes false-positive offline state.
- The next accepted heartbeat flips Offline back to Active at `DeviceLifecycleHandlers.cs:168-173`.

## Deterministic reproduction

1. Create/update an IoT device with `HeartbeatIntervalSeconds=3600` (valid input).
2. Keep the device healthy but do not produce sensor batches during the interval (for example a heartbeat-only device or temporary BMS outage).
3. Send one heartbeat, then wait slightly over 300 seconds.
4. Offline worker marks the device Offline and emits `DeviceOffline` alert/event.
5. At the valid one-hour cadence, the next heartbeat changes it back to Active; the cycle repeats.

## Actual result

An allowed heartbeat schedule is incompatible with the system's liveness detector and creates oscillating false incidents.

## Expected result

Offline detection must derive a per-device deadline from its configured heartbeat cadence (with a documented grace/missed-heartbeat count), or validation must reject intervals that cannot satisfy the global threshold.

## Impact

- False offline alerts/notifications and operational noise.
- Device status dashboards oscillate despite a healthy, correctly configured device.
- Real outages become harder to distinguish from configuration-induced false positives.

## Acceptance criteria

- Use a per-device cutoff such as `max(global minimum, HeartbeatIntervalSeconds × missed-heartbeat allowance)` or constrain configuration accordingly.
- Define how successful telemetry and MQTT LWT interact with heartbeat liveness.
- Recalculate safely after interval changes.
- Add tests for 10s, 60s, 300s, and 3600s intervals; no device is marked offline before its own deadline.
- Verify exactly one offline event/alert per real transition and clean recovery.
