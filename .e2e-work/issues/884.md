# #884 — [IoT][Firmware Build][Production] esp32-s3-real undefines the real-BMS flag and ships mock telemetry

Priority: priority: P1
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/884

---

## Component
IoT firmware — PlatformIO production/real-BMS build configuration

## Evidence and runtime-equivalent reproduction
1. Clean and build `pio run -e esp32-s3-real` successfully.
2. Inspect the actual compiler command. It contains `-DUSE_MOCK_BMS=0` followed later by `-UUSE_MOCK_BMS`; the later undef wins.
3. `include/config.h:77-81` and `config.example.h:136-138` then see the macro undefined and default it back to `1`.
4. Inspect the clean artifact: `strings .pio/build/esp32-s3-real/firmware.elf` contains `[bms-source] MOCK mode` and no REAL-mode banner.
5. Mock and supposed real builds originally reported identical RAM/Flash size, consistent with the same compiled branch.

`platformio.ini:112-121` intends the opposite order (`-UUSE_MOCK_BMS`, then `-DUSE_MOCK_BMS=0`), but PlatformIO/SCons emits macro definitions before undefines in the effective compile command.

## Actual
The `esp32-s3-real` target compiles with `USE_MOCK_BMS=1`. A successful CI build does not exercise or ship the Modbus, INA226, DS18B20, or SHT31 real polling branch; flashed devices emit generated mock battery data.

## Expected
The real target must deterministically compile with `USE_MOCK_BMS=0`, fail compilation if that invariant is not true, and produce an artifact provably containing the REAL path.

## Impact
Production hardware can report fabricated telemetry while real sensor failures remain invisible. CI has provided a false green signal for the hardware integration path.

## Acceptance criteria
- Fix flag precedence without relying on a trailing `-U`/header default interaction.
- Add a compile-time assertion/error for the selected environment and distinct `FW_BUILD_ENV`.
- CI inspects/preprocesses the artifact and asserts REAL banner/code for `esp32-s3-real`, MOCK for dev.
- Build hashes/sizes or symbols must differ for the two targets.
- Add hardware-path tests and a boot smoke proving Modbus/sensor initialization is attempted in the real artifact.
