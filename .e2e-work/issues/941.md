# #941 — [NotificationService][DLQ Monitoring] Deleted error queues leave stale non-zero Prometheus gauges and permanent false alerts

Priority: priority: P3
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/941

---

## Component

`[NotificationService][RabbitMQ DLQ][Prometheus][Alerting]`

## Severity

P3 Standard — deleting a recovered error queue leaves a permanent false critical alert until service restart.

## Source evidence

- `NotificationDlqMonitorBackgroundService.cs:125-133` updates `notification_dlq_size{queue=...}` only for `_error` queues present in the current RabbitMQ `/api/queues` response.
- The worker correctly writes zero when an existing queue becomes empty, but it does not remember prior labels or remove/reset labels for queues that disappear.
- Prometheus client gauges retain their last labeled value until explicitly changed or removed.
- `monitoring/prometheus/alert-rules.yml:596-603` fires the critical `NotificationDlqNotEmpty` alert whenever `sum(notification_dlq_size) > 0`.

## Deterministic reproduction

1. Return `foo_error` with `messages=5` from the management API and run one poll.
2. Observe `notification_dlq_size{queue="foo_error"} 5`.
3. After investigating/replaying, delete `foo_error` from RabbitMQ.
4. Return `[]` from the next `/api/queues` poll.
5. The `foreach` updates no label, so the metric remains 5 and the critical alert continues indefinitely.
6. Restarting NotificationService clears the in-process metric, proving the alert was stale rather than a live queue.

## Actual

Queue disappearance is interpreted as “no update,” not a zero/removal transition.

## Expected

Every successful poll must make exported label state exactly match the current set of RabbitMQ error queues.

## Impact

- Operators receive a permanent false critical incident after legitimate queue cleanup.
- Real notification failures become harder to distinguish from stale telemetry.
- Alert fatigue can cause actual DLQ events to be ignored.

## Acceptance criteria

- Track the prior queue-label set and set missing queues to zero or remove their labels on every successful poll.
- Do not clear gauges when the management API poll itself fails.
- Avoid cardinality leaks from repeatedly created/deleted queue names.
- Add tests for nonzero→zero, nonzero→deleted, renamed/recreated queue, failed poll, and service restart.
- Verify `NotificationDlqNotEmpty` resolves after queue cleanup without restarting the service.

## Dedupe

No issue through #938 covers stale DLQ gauge labels. This is separate from consumer retry/DLQ routing and notification delivery failures.
