# #921 — [IoT][BMS][Availability] Unused 500 ms timeout lets offline multi-drop polling block the main loop for about 16 seconds

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/921

---

## Component

`IoT firmware` — real BMS Modbus multi-drop polling and main-loop availability.

## Summary

Firmware documents/configures a 500 ms Modbus timeout through `BMS_POLL_TIMEOUT_MS`, but never applies it. The pinned ModbusMaster library uses a hard-coded 2,000 ms response timeout. With one retry and four configured BMS unit IDs, an offline RS485 bus blocks the single Arduino loop for about 16 seconds per poll, delaying safety sensors, heartbeat, OTA verification, queue flush, and MQTT servicing.

## Evidence

- `../iot/firmware-esp32/include/config.example.h:158-163` configures 4 unit IDs, `BMS_POLL_TIMEOUT_MS=500`, and one retry.
- `../iot/firmware-esp32/src/bms/modbus_bms.cpp:102-131` performs each request plus retry but never references the timeout setting.
- `modbus_bms.cpp:209-228` polls every configured unit synchronously in sequence.
- Pinned `ModbusMaster/src/ModbusMaster.h:251-252` hard-codes `ku16MBResponseTimeout=2000` ms, and `ModbusMaster.cpp:800-803` waits for it inside the transaction loop.
- `../iot/firmware-esp32/src/main.cpp:241-255,530-539` calls the synchronous BMS poll from `ingestOnce()`.
- `main.cpp:542-567` cannot run queue flush, OTA, heartbeat, SHT31, MQ-2, water-leak, LED, or stats until that call returns.

## Deterministic reproduction

1. Build/run the `esp32-s3-real` profile with the documented defaults: 4 BMS unit IDs, one retry, configured timeout 500 ms.
2. Disconnect or power off every Modbus slave while ESP32 itself remains online.
3. Each unit performs two transactions at the library's 2,000 ms hard-coded timeout.
4. Total blocking time is approximately `4 units × 2 attempts × 2,000 ms = 16,000 ms`, plus settle delays.
5. Observe that the following main-loop ticks do not execute during the block, despite a 5-second ingest interval and shorter safety-sensor poll intervals.

## Actual result

The advertised 500 ms timeout has no effect. Failure of the BMS bus stalls unrelated networking, OTA, heartbeat, and environmental safety work in the single-threaded loop.

## Expected result

One failed peripheral bus must not block unrelated safety/network tasks beyond the configured timeout; the effective timeout must match configuration and the poller must have a bounded total budget.

## Impact

- Gas/water incident detection and reporting can be delayed by roughly 16 seconds per failed poll.
- Heartbeat, OTA health/rollback checks, MQTT polling, and queued telemetry are starved.
- The provisioned 5-second telemetry cadence cannot be met under a common partial-hardware failure.
- Adding more unit IDs linearly increases the stall.

## Acceptance criteria

- Apply an actually supported per-request timeout or replace/wrap the library with a configurable transaction deadline.
- Enforce a bounded total multi-drop poll budget and yield/state-machine behavior so unrelated ticks continue.
- Report individual BMS timeout health without blocking other units/sensors.
- Add a real-target/fake-clock test for all slaves offline and one slave offline.
- Assert maximum loop latency and that OTA/heartbeat/MQ-2/water ticks still run within their deadlines.
- Remove or fail build on unused timeout configuration.
