# #912 — [BatteryService][OTA Storage Contract] Neither documented storage mode produces a usable artifact URL

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/912

---

## Component

`[BatteryService][OTA Storage Contract]` — artifact persistence and URL generation in both documented production storage modes.

## Source evidence

### Default local/PVC mode

- Compose/Helm defaults leave `Firmware__PublicBaseUrl` empty.
- `AdminIotFirmwareReleasesController.cs:328-332` then returns a relative artifact URL `/firmware-storage/{file}` after upload.
- `CreateIotFirmwareReleaseCommand.cs:45-46` accepts only an absolute URI.
- The upload response instructs the caller to reuse its URL/SHA for release creation, but that exact URL is rejected.

### Documented object-storage/CDN mode

- `deploy/README.md:395-411` instructs operators to disable the PVC, set an empty `StorageRoot`, and provide a CDN `PublicBaseUrl`.
- `Program.cs:138-149` and the controller at `:296-332` still write only to a local fallback directory and concatenate the CDN base with the filename.
- No S3/CDN/object-storage upload adapter exists, so the returned external URL names an object that was never uploaded; the local fallback disappears on pod restart when persistence is disabled.

## Steps to reproduce

1. Default mode: upload a valid small `.bin`, receive 201 with a relative URL, then POST create-release using the returned data. Observe validation 400 for non-absolute `ArtifactUrl`.
2. Object mode: follow the documented no-PVC/CDN configuration and upload a valid binary. Request the returned CDN URL and restart the pod. Observe the object does not exist externally and local data is ephemeral.

## Actual result

Neither documented storage mode produces a durable URL that can complete upload → create release → device download.

## Expected result

One storage abstraction persists the artifact first and returns an externally reachable durable absolute URL whose semantics are accepted by release creation.

## Impact

OTA rollout cannot be completed in default production and can register broken URLs in object mode. Devices receive unusable download locations and uploaded files become orphaned/lost.

## Acceptance criteria

- Implement a storage abstraction with real local/PVC and S3-compatible/object-storage adapters.
- Local mode returns an absolute externally reachable URL (or release creation deliberately resolves trusted relative paths consistently).
- Object mode uploads successfully before returning a CDN/object URL; rollback the object on failed metadata commit.
- Add production-profile E2E for upload → create release → authenticated device check → binary download/SHA in both modes.
- Validate startup configuration and reject unsupported combinations instead of silently falling back local.

## Dedupe note

Distinct from #905, which covers embedded version/post-flash equality; this issue covers artifact durability and URL reachability before flashing.
