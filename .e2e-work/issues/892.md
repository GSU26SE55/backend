# #892 — [IoT][MQTT][Security] Provisioning scripts expose plaintext broker passwords in process arguments and logs

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/892

---

## Component

`[IoT][MQTT][Security]` — Mosquitto device provisioning and broker bootstrap scripts.

## Evidence

- `iot/infra/mqtt/scripts/add-device.sh:42-43` presents stdin mode as the recommended non-logging path.
- Regardless of input mode, `add-device.sh:95-98` expands the plaintext value as the final argument of `docker run ... mosquitto_passwd -b ... "$PASSWORD"`.
- `iot/infra/mqtt/mosquitto/bootstrap.sh:61-64` does the same for the shared `backend-bridge` credential.
- `bootstrap.sh:74-83` additionally prints the complete generated/shared plaintext password to stdout.
- The explicit argv mode at `add-device.sh:41,48-49` and `bootstrap.sh:10-12,25-33` can also persist operator-supplied passwords in shell history.

The existing E2E MQTT issues (#784, #829, #848, #870) cover credential synchronization, authorization, deployment placeholders, and connection-state handling; none covers plaintext exposure by these operational scripts.

## Steps to reproduce

1. Run `infra/mqtt/scripts/add-device.sh <device>` and enter a recognizable test secret through the recommended hidden stdin prompt.
2. While the spawned `docker run` / `mosquitto_passwd -b` command is active, inspect the process command line (`ps`, `/proc/<pid>/cmdline` on Linux, or an equivalent process monitor).
3. Observe the test secret as a command-line argument even though it was entered through stdin.
4. Run `infra/mqtt/mosquitto/bootstrap.sh --reset` in a disposable broker setup and capture stdout as a CI/log collector would.
5. Observe `Password: <plaintext>` and `Mqtt__Password=<plaintext>` in the captured output; the same value is also passed to `mosquitto_passwd -b` through argv.

## Actual result

MQTT credentials are exposed to process inspection and, for bootstrap, stdout/log capture. Supplying the device password through the advertised stdin mode only hides terminal echo; it does not keep the secret out of child-process arguments.

## Expected result

Provisioning must transmit secrets through a protected stdin/file-descriptor or another secret channel that does not place plaintext in argv. Generated credentials must not be emitted to ordinary stdout or CI logs, and documented invocation should not encourage secrets as positional arguments.

## Impact

An operator, co-tenant process, diagnostic agent, CI collector, or process-monitoring integration can recover a device credential or the privileged `backend-bridge` credential. A stolen bridge credential can subscribe/publish across `solar/#`; a device credential enables impersonation until rotation.

## Acceptance criteria

- Remove plaintext password arguments from both the host script and the container process command line.
- Make hidden stdin (or a protected secret file/FD) the only supported input path; reject positional plaintext passwords.
- Deliver a generated bootstrap credential through an explicitly protected mechanism and never normal stdout/log output.
- Add an automated regression test using a recognizable sentinel and assert it is absent from child argv and captured stdout/stderr.
- Document rotation/revocation steps for credentials that may already have been exposed.
