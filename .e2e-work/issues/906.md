# #906 — [BatteryService][IoT][Heartbeat Contract] Accepted resource and temperature fields are silently discarded

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/906

---

## Component

`[BatteryService][IoT][Heartbeat Contract]` — persistence of device resource and thermal health fields.

## Source evidence

- `overall.md:9478-9494` defines heartbeat `Cpu`, `MemoryUsageMb`, `DiskFreeMb`, `Temperature`, `ConnectedSensorCount`, `LocalQueueDepth`, IP, and signal fields; §52.4 requires a heartbeat row to retain them. The implementation checklist at `overall.md:5102` explicitly calls out ESP32 field mapping.
- `DeviceLifecycleCommands.cs:59-68` accepts `Cpu`, `DiskFreeMb`, `Temperature`, and `MemoryUsageMb` in `IotDeviceHeartbeatCommand`.
- `DeviceLifecycleHandlers.cs:154-164` persists only firmware, RSSI, free-memory percentage, uptime, queue depth, device timestamp, and skew. The four accepted fields are never mapped.
- `IotDeviceHeartbeat.cs:8-35`, its EF configuration, and the model snapshot have no columns for those values (or `ConnectedSensorCount`).
- IoT firmware `telemetry/heartbeat.cpp` actively sends `Temperature` and `MemoryUsageMb`, so this is a live cross-repository contract loss rather than an unused DTO field.

## Steps to reproduce

1. POST a valid authenticated heartbeat with recognizable values such as `cpu=35.5`, `memoryUsageMb=512`, `diskFreeMb=14000`, and `temperature=48.2` plus a valid device timestamp.
2. Observe HTTP 200.
3. Re-query the persisted heartbeat row through the repository/database and any history API.

## Actual result

The request succeeds but the accepted resource/thermal fields have no storage columns and disappear permanently. Only the older generic subset is retained.

## Expected result

Every documented and accepted heartbeat health field is validated, stored, and returned round-trip, or the API explicitly rejects/removes unsupported fields instead of acknowledging and discarding them.

## Impact

Operators lose device temperature, memory, CPU, disk, and sensor-count history. Memory pressure/overheating cannot be diagnosed or alerted from the monitoring data despite devices reporting it successfully.

## Acceptance criteria

- Add the documented columns/entity/configuration/migration with appropriate precision and bounds.
- Map every DTO field in the handler and expose it through heartbeat history/detail/reporting where specified.
- Clarify free-versus-used memory semantics consistently across ESP32, backend, API docs, and UI.
- Add API + real database integration tests that POST distinct values and assert exact round-trip persistence.
- Add validation for impossible resource/temperature/count values and backward compatibility for devices sending the older subset.

## Dedupe note

Distinct from #807 (invalid operational values accepted) and #809 (firmware always reports queue depth zero); this issue is silent loss of valid fields that are already sent and accepted.
