# #898 — [AuthService][Password Reset][Transactional Consistency] DB failure consumes reset token before password commit

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/898

---

## Component

`[AuthService][Password Reset][Transactional Consistency]` — reset-token single-use marker versus password transaction.

## Evidence

- `ResetPasswordCommandHandler.cs:43-61` reserves `pwd_reset_used:{jti}` with Redis `SET NX` before any database mutation.
- Password and refresh-token changes plus `SaveChangesAsync` occur later at `:64-100`.
- Access-token revocation also occurs before database commit at `:91-92`.
- No failure path releases or compensates the Redis marker when persistence fails.

This is distinct from #818: it concerns the password-reset recovery token state machine, not HTTP idempotency middleware.

## Steps to reproduce

1. Use a valid, unused password-reset token and allow the Redis `SET NX` to succeed.
2. Inject a `DbUpdateException` from `SaveChangesAsync`.
3. Confirm the password remains unchanged and the first request returns an internal failure.
4. Retry the same valid reset link after the transient database failure is removed.

## Actual result

The retry returns 401 / “Reset token đã được sử dụng” because the Redis marker survived even though no password change committed. Revocation side effects may also diverge from database state.

## Expected result

A reset token becomes consumed only with a successfully committed password change. A transient pre-commit failure remains safely retryable, while concurrent successful consumption still permits exactly one commit.

## Impact

Users can permanently burn their only recovery link during a transient DB outage and remain locked out. Cross-store partial effects also make incident recovery and auditing unreliable.

## Acceptance criteria

- Implement a reservation/commit/release state machine or store consumed JTI in the same durable transaction.
- Release/expire an uncommitted reservation on every failure path.
- Verify retry after a pre-commit DB failure succeeds.
- Verify two concurrent requests produce exactly one password commit and one controlled 401/409 loser.
- Keep token/session revocation consistent with the committed password state.

## Verification performed

Existing targeted reset-password tests pass (3/3); none injects a database failure after the Redis reservation.
