# #922 — [IoT][BatteryService][Heartbeat ACK] Firmware discards server cadence, clock-skew, and OTA controls

Priority: priority: P2
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/922

---

## Component

`BatteryService` ↔ `IoT firmware` — heartbeat acknowledgement/control contract.

## Summary

BatteryService returns `NextHeartbeatInSeconds`, `ClockSkewWarning`, server time, and `FirmwareUpdateAvailable` on every heartbeat, and its API contract explicitly tells firmware to apply these controls. ESP32 sends heartbeat through a response-discarding helper and never parses the acknowledgement. Runtime interval changes are ignored, clock-drift recovery is not triggered, and OTA hints cannot accelerate a required update.

## Evidence

- `services/BatteryService/src/BatteryService.Application/CQRS/Handler/IotDevice/DeviceLifecycleHandlers.cs:185-196` returns the four control fields from live device state.
- `services/BatteryService/src/BatteryService.Api/Controllers/IotDevicesController.cs:130-138` documents that the device should use `NextHeartbeatInSeconds`, auto-resync on clock warning, and act on firmware-update hints.
- `../iot/firmware-esp32/src/telemetry/heartbeat.cpp:96-121` calls `httpPostJson`, checks only the status code, and never parses a body.
- `../iot/firmware-esp32/src/net/http_client.cpp:243-247` invokes the internal client with a null response buffer.
- `../iot/firmware-esp32/src/telemetry/heartbeat.cpp:125-159` changes cadence only through `heartbeatBegin`/`heartbeatSetInterval`; no ACK path calls the setter.
- `../iot/firmware-esp32/src/provision/provision.cpp:138-151` persists the interval only during provisioning.
- `../iot/firmware-esp32/src/main.cpp:94-120` marks provisioning done and does not refresh the config on later heartbeats.

## Deterministic reproduction

1. Provision a device with `HeartbeatIntervalSeconds=60`; firmware stores/uses 60 seconds.
2. Change the device interval through the admin API to 10 seconds.
3. Let the device send its next heartbeat. BatteryService returns HTTP 200 with `data.nextHeartbeatInSeconds=10`.
4. Firmware discards the body and keeps `s_intervalMs=60000`; later heartbeats remain 60 seconds apart.
5. The same trace shows `clockSkewWarning=true` or `firmwareUpdateAvailable=true` is also ignored.

## Actual result

HTTP success is counted, but none of the server's heartbeat controls affect device behavior.

## Expected result

Firmware must validate and apply the acknowledgement atomically, with bounded values and explicit fallback when the body is invalid.

## Impact

- Admin heartbeat-cadence changes do not take effect without reprovision/reset, causing stale offline detection or excess load.
- Clock-drift warnings cannot request immediate resynchronization.
- Required firmware updates may wait for the separate hourly poll instead of acting on the server hint.
- Backend exposes a control-plane contract that the shipped device cannot consume.

## Acceptance criteria

- Receive and parse the full `CommonResponse<IotHeartbeatAckDto>` body.
- Validate/apply `NextHeartbeatInSeconds` within [10, 3600] and persist the chosen cadence when required.
- Trigger immediate NTP resync on `ClockSkewWarning` and schedule an immediate bounded firmware check on `FirmwareUpdateAvailable`.
- Preserve the current cadence and emit a diagnostic metric/log on malformed ACK.
- Add cross-repository tests for live interval change, clock warning, firmware hint, malformed body, and retry/idempotency behavior.
