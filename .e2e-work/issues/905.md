# #905 — [IoT][OTA][Version Contract] Shipped firmware version cannot be registered and makes post-flash verification fail

Priority: priority: P1
State: OPEN
URL: https://github.com/GSU26SE55/backend/issues/905

---

## Component

`[IoT][OTA][Version Contract]` — firmware build metadata, BatteryService release registration, and post-flash verification.

## Source evidence

- `iot/firmware-esp32/platformio.ini:59-65` hard-codes the production/main firmware `FW_VERSION` as `0.1.0-sprint4`; `esp32-s3-real` inherits it at `:116-121`.
- `BatteryService.Application/.../CreateIotFirmwareReleaseCommand.cs:39-42` accepts only `^\d+\.\d+\.\d+$`, so `0.1.0-sprint4` cannot be registered as a release target.
- Firmware check sends that build constant as `currentVersion` and compares strings exactly (`ota_update.cpp:292-320`).
- Before flashing, it persists the backend target string at `ota_update.cpp:341-350`.
- After reboot, `ota_update.cpp:369-378` requires `strcmp(FW_VERSION, targetVersion) == 0`; any mismatch is recorded as Failed and the target is marked bad.
- `config.example.h:229-232` explicitly documents that exact equality is mandatory, but the shipped build flag violates the backend's accepted format.

## Deterministic reproduction

1. Build either main firmware environment without editing source. Its embedded version is `0.1.0-sprint4`.
2. Attempt to create a BatteryService firmware release with version `0.1.0-sprint4`; validation rejects it because the only accepted form is `X.Y.Z`.
3. Register the closest valid target `0.1.0` and upload the unchanged artifact.
4. Let a device check, download, verify SHA, flash, and reboot.
5. `handleVerify()` compares running `0.1.0-sprint4` with target `0.1.0`, reports `boot version mismatch`, clears verification, and marks `0.1.0` bad even though the intended binary booted.

## Actual result

No release record can have the exact version embedded in the shipped firmware. Using a backend-valid version makes post-flash verification fail deterministically and blocks/poisons subsequent delivery of that target.

## Expected result

The build pipeline and backend share one validated version value. The version stored in release metadata, embedded in the binary, returned by firmware-check, and observed after reboot is byte-for-byte identical.

## Impact

The completed OTA feature cannot reach Success with artifacts built from the checked-in production environments. Operators can misdiagnose a healthy image as failed/bad, lose rollout capability, and remain on vulnerable or faulty firmware.

## Acceptance criteria

- Define one release version input accepted by both build and backend; either support validated SemVer pre-release identifiers end-to-end or embed strict `X.Y.Z`.
- Inject the release version in CI rather than leaving a stale sprint literal in `platformio.ini`.
- Extract/attest the embedded version from the produced artifact and reject upload/registration when it differs from release metadata.
- Add an E2E fixture covering create release → firmware-check → flash/reboot simulation → Success with exact version equality.
- Add a negative test proving a mismatched artifact is rejected before rollout, not discovered only after flashing.
- Ensure bad-version state is not written for a metadata mismatch caused by the release pipeline itself.
